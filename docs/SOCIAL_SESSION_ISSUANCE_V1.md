# Social session issuance V1 operation contract

Dormant source, PostgreSQL owner. Source installation does not activate routes in the default factory. The database commit authorizes one exact Social client/issuer, subject/device/binding and accepted phone handoff. A later cookie is retryable presentation of that same decision. No atomic PostgreSQL-plus-cookie delivery is claimed.

## Composition and provisioning

Apply the new source migration only after the existing binding, authorization, mobile and OAuth lifecycle migrations, in a separately authorized transaction. Provision exactly one `social_session_issuers` row per eligible OAuth viewer client, recording its confidential backend client ID and service principal. Registration is explicit, never auto-created from a request or historical handoff; identity is immutable and deactivation is monotonic. Construct mobile storage with `issuance_client_id`, the existing lifecycle with that client, and the new service with the same session factory and recorded backend/principal. Construct the issuance ingress with the actual durable replay adapter and the existing infrastructure signing/verification configuration. Only `install_session_issuance(app, runtime, enabled=True)` registers its five routes. No environment fallback, process-local authority ledger or default factory activation exists.

## Credentials, HTTP and schemas

Prefix P = `/internal/v1/social/session-issuance`; issuer I is the configured exact lowercase HTTPS origin. Assertion audience = I + P + `/service-token`; resource audience = I + P; scope = `social:session-issuance:manage`; purpose = `social_session_issuance_v1`. Existing mobile desktop/phone/exchange/invalidate and Full Directory credentials cannot cross this boundary. Backend possession grants no human authority. Service keys are existing trusted infrastructure inputs, never participant keys.

`POST P/service-token` uses exact `application/x-www-form-urlencoded`, one each of grant_type=client_credentials, configured client_id, client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, client_assertion and the exact scope. Existing confidential assertion verification and PostgreSQL replay consumption precede token release. Retry lost service-token delivery with a fresh assertion. Success is `{access_token, token_type:"Bearer", expires_in:60, scope}`.

All other requests are POST with exact `application/json`, positive Content-Length <=65536, no query, Content-Encoding or Transfer-Encoding, and one service bearer in Authorization. Strict UTF-8 flat JSON rejects unknown, duplicate, missing, nested or non-string members. All JSON values below are exact lowercase hex64. Resolve/revoke additionally require the canonical human bearer in `X-HODLXXI-Viewer-Authorization`; issue/recover reject that header and require the original phone proof instead.

| Path | Exact JSON members | Authority/result |
| --- | --- | --- |
| `/issue` | pairingId, revision, authorizationDigest, verifier, deliveryKey | Original persisted handoff and phone verifier, current prerequisites, single committed result |
| `/recover` | same | Bound existing issuance only; absent issuance cannot be created |
| `/resolve` | issuanceId | Exact canonical mobile viewer credential and current original authority |
| `/revoke` | issuanceId | Exact original mobile viewer credential, including expired/revoked, revokes only that issuance |

The phone generates a separate random 32-byte deliveryKey before first issuance and preserves it with its original transient verifier until delivery is resolved. It is not a device key or a new participant signature. The stored delivery commitment is SHA256 of ASCII `HODLXXI_SOCIAL_SESSION_DELIVERY_V1`, NUL, and the canonical compact sorted-key JSON array `[viewerClientId,backendClientId,servicePrincipal,pairingId,verifier,deliveryKey]`. Neither value is persisted in plaintext. The first committed context wins; changed delivery keys cannot mint again or recover another result. Possession of the same original phone proof represents the same phone transaction; QR secret alone does not.

Issue/recover success has exactly `{receipt,currentActive,subject,viewerAccessToken}`. Receipt is exactly `{schema:"hodlxxi.social_session_issuance.v1",version:1,issuanceId,issuedAt,expiresAt}`. UTC dates use whole-second `YYYY-MM-DDTHH:MM:SSZ`. Receipt bytes and original dates are immutable. Active delivery provides canonical subject and real canonical OAuth bearer only on the confidential response. Inactive history has currentActive=false and null subject/viewerAccessToken. This status is a transaction-time observation and cannot authenticate a delayed cookie on its own. Historical handoff created/recovered responses remain unchanged with freshIssuanceAuthorized=false.

Resolve success is exactly `{receipt,subject,currentActive:true}`. Missing/expired/revoked/mismatched authority has no authentication success. Revoke success is exactly `{schema:"hodlxxi.social_session_revocation.v1",version:1,issuanceId,status:"revoked"}`. All errors are generic: invalid_request/400, invalid_credential/401 for backend/header problems, session_issuance_unavailable/503 for proof/authority/storage failures. Disabled/unregistered routes provide no capability. Responses include Cache-Control:no-store and Pragma:no-cache; unknown methods/paths, redirects and oversized bodies receive bounded generic errors. Nothing is transported in URLs or logs.

## State, identifiers and issuance decision

`social_session_pairing_parents` attaches an offer to the exact canonical OAuth token/Session generation during the SAME database transaction as offer creation. The existing authenticated resolver selects that Session; its original mobile continuity commitment remains unchanged. PostgreSQL insertion-transaction and state checks prohibit late adoption even of an old unscanned offer. No old handoff lacking this provenance can issue.

`social_session_issuances` has the handoff operation ID as primary key. Unique constraints separately own issuanceId, canonical token JTI, original request ID and digest. Foreign keys bind source handoff, original parent mapping, exact client/issuer and OAuth token User/client. The immutable row records method=qr_desktop_v1, accepted register/rotate/adopt operation, canonical subject/device/binding, original request/digest/revision, delivery commitment, issuance second and absolute expiry. Revoke cannot issue. Issuance ID is a non-bearer selector, distinct from token JTI, Session ID, digest, binding ID and all phone proof inputs.

Inside one PostgreSQL READ COMMITTED transaction the service rereads and verifies the original accepted proof at acceptance time, reconstructs the frozen handoff through the real phone exchange verifier, then checks current User/client/issuer, original OAuth/browser generation, exact continuity, original exclusive deadlines and unchanged active binding. Current-Full is verified transactionally at initial issuance and again after writes. Token scope is the canonical basic identity scope `openid profile`; Full/Operator/sponsor/CRT/spending/friendship/messaging readiness are not granted. The same token digest and immutable issuance row commit together. Every failure before commit rolls both back and releases no credential.

## Locking and linearization

The operation advisory lock and row serialize identical issuance/recovery/revoke with existing mobile commands. Before new authority, the service takes the global request lock and reuses the actual binding mutation sequence: Current-Full subject advisory lock, User row, device namespace, global public-key guard and sorted public keys. It then locks client, issuer registration, original browser, parent token and Session; binding row is locked before persistence. Existing binding writers and lifecycle writers share these locks or the exact parent/binding rows. Database guards independently lock and check owners when inserting the issuance. Revocation never needs a new operation's lock and cannot invalidate replacements by subject alone.

PostgreSQL commit is the authority decision linearization point. The service samples trusted time after waits and rechecks deadlines after writes, with no skew allowance. Canonical downstream viewer validation linearizes at its real persisted token/User record read; issuance resolver repeats validation after current-authority locks. Revocation commits before a new validation read imply denial. A request already admitted before revocation may finish; no instantaneous cancellation of in-flight work is claimed. Cookie delivery has no authority linearization and must be checked through resolve on authenticated use.

## Canonical viewer path and recovery

The credential uses the existing RS256 signer, canonical access-token contract/metadata/scope policy and OAuthToken SHA-256 digest storage. No mobile generation is inserted into oauth_session_generations, no fake verified browser is created and no ordinary OAuth exchange is invoked. Desktop replacement behavior is unchanged. Existing introspection and confidential Full Directory/device/recipient validators can verify the real token via their current canonical bearer path.

Bound active recovery recreates byte-identical RS256 output from immutable issuance fields and the original existing infrastructure key ID retained in token metadata, then compares its SHA-256 with the original digest. It never generates a new JTI, expiry or signing identity. Neither plaintext bearer nor phone verifier is stored in a generic JSON ledger. Missing/retired original key or changed signing representation fails closed: no credential is returned and no second grant can be created. A retry can succeed only if original trusted material is restored; otherwise the authority expires/revokes and a separately authorized new phone transaction is needed. Signer output is validated before first release.

Recovery after expiry/revocation returns only immutable history, never a bearer. Loss of issuer-local state is not rollback evidence. Lost response before commit permits a retry only if no issuance committed and prerequisites still hold; recover never creates. Lost response after commit returns the same result with the same phone/delivery proofs while active. A failed commit has no usable released credential. No retry acquires a second participant signature automatically.

If the Social record is lost after the phone verifier and delivery key were discarded, a receipt or cookie ID cannot restore credential possession. This is terminal local delivery loss: fail closed, never infer that no grant exists, and never automatically issue another authority. Recovery tests retaining the original phone context cover reconciliation before delivery acknowledgement. A separately authorized new login/pairing is required when that context is gone; expiry and parent/binding invalidation still end the original authority.

Revoke reconstructs exact original signed bytes and compares them to the supplied original viewer credential, under the exact immutable issuance owner. Expiry/current User activity is irrelevant only for this revocation-only operation; it returns no principal. An ID, service token, arbitrary JWT or replacement credential cannot substitute. This lets the BFF discard the original phone verifier/deliveryKey after delivery and keep its existing protected viewer credential for logout.

## Lifetime and invalidation

Absolute expiry is the earliest of original pairing/accepted semantic/exchange, exact binding and parent Session/token deadlines, capped within the original maximum 300-second pairing window. It is deliberately short; no renewal/refresh/extension route exists. Later Social stores and cookies must use that absolute deadline, not sessionTtlSeconds added at recovery time.

Initial issuance is denied after parent logout/replacement. Already issued mobile authority is revoked transactionally on parent token or Session invalidation/shortening, browser logout/replacement, User deactivation/subject change and OAuth client deactivation. Any change to its exact accepted binding, including real revoke/rotation retirement, revokes the mobile token. Client scope/metadata changes and issuer deactivation also revoke existing mobile tokens. Database token guards forbid identity changes, extension or resurrection; shortening revokes. Restoring user/client/binding state cannot resurrect a revoked token. Explicit phone logout affects one exact issuance only. Current-Full revocation does not revoke basic authentication under this chosen policy, but all Full-protected consumers independently check current evidence and deny privilege; new issuance requires current Full.

Retain issuance, parent, handoff, replay and token history indefinitely in V1; no deletion/pruning contract is supplied. Roll back uncommitted migration DDL in a disposable rehearsal. After use, disable admission and revoke authority while preserving ledgers and guards. Dropping used tables is not rollback.

## Later Social consumer obligations

The pinned consumer fixture is `tests/fixtures/social_session_issuance_v1.json`; the runnable test-only BFF substitute is `tests/helpers/social_session_issuance_consumer.py`. Social's `authenticatedSessionContext`, `authenticatedSession`, `authenticatedSubject` and `/auth/session` must await current resolution for mobile records on every authenticated use. Existing full-directory, messaging device/recipient and opaque-capability clients continue to send the canonical `viewerAccessToken`; their separate entitlement/authorization checks remain required. `createSessionStore` must accept bounded absolute issuance dates for these records instead of resetting its configured TTL. Local mobile records have `{subject,viewerAccessToken,issuanceId,issuedAt,expiresAt}`, with absolute millisecond dates. `/auth/logout` must deliver exact revoke with its retained viewer credential, acknowledge the durable result, then clear local state; retries must use the same issuance ID. A local record or cached resolve response is never final authority. Social source remains unchanged. Before activation it must add the confidential issuer client, bind delivery context to the original phone transaction, create bounded absolute local records, asynchronously resolve on authenticated use, deliver exact logout/retry acknowledgement and complete UI/key reconciliation. Stale-cookie browser logout local cleanup and the general runner shutdown followups remain separate. None of these source tests claims deployed mobile login or messaging readiness.
