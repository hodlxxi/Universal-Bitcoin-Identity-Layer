# Social mobile device authorization contract V1

This is the canonical cross-repository protocol for Phase 1 of Social messaging
completion. Its implementation is dormant pure parsing, canonicalization,
signature verification, and injected state-transition seams. It adds no HTTP
route, factory composition, durable adapter, migration, configuration, session
issuer, or live onboarding. It does not complete private messaging.

The product is complete only when two real Current-Full participants can send,
receive, and locally decrypt private messages. Three independent checks stand
between that goal and this contract: participant authentication, authorization
of one exact messaging device, and ciphertext messaging. OAuth/session possession
alone does not authorize a device. A phone must be able to complete device
authorization through a bound LEGACY login without NIP-07 or NIP-46. Desktop
NIP-07 approval is optional. Social's public-Nostr **Connect signer** control is
independent and cannot become a private-messaging prerequisite.

## Existing login: confirmed source behavior

Social's `src/server/social-oauth-bff.mjs` redirects `/auth/login` to UBID OAuth
with a one-shot browser transaction, state, and S256 PKCE. Its callback consumes
the transaction, exchanges the code using confidential client authentication,
introspects the access token, and creates an unrelated opaque Social session.
The accepted introspection subject must be a lowercase 64-hex x-only key. These
operations do not carry a messaging proposal today.

UBID's factory registers `app/blueprints/auth.py`. `app/browser_routes.py`
renders the LEGACY form with a UUID-v4 string generated by `app/utils.py`, stores
it in the browser session with a timestamp, and submits the displayed string,
compressed public key, and pasted signature to `/verify_signature`. The handler
derives a legacy P2PKH address from the compressed key and calls Bitcoin Core
`verifymessage(address, signature, challenge)`. With no supplied key, the legacy
handler tries configured public-key candidates. The bound-device flow requires
an explicit canonical public-key hint before issuance, so the subject is already
part of the immutable proposal. A hint does not prove identity.

The wallet signs the UUID text as a Bitcoin Signed Message, not a Nostr event,
OAuth code, device JSON, or raw SHA-256 digest. The exact digest is SHA256 twice
over `CompactSize(24) || "Bitcoin Signed Message:\n" || CompactSize(36) || UUID`.
The compressed-P2PKH compact signature has 65 bytes, base64 encoded; headers
31–34 encode compression plus the recovery ID. The new offline verifier uses
the existing coincurve dependency to recover the compressed key and requires
exact equality, then exact x-only subject equality. No wallet API is invented.
This establishes compatibility with the existing verifier's signed message;
it is not a claim that a particular phone or wallet was exercised.

Successful LEGACY verification calls `persist_verified_browser_subject` to
canonicalize, create, and reread the active canonical user. The browser session
retains the verified compressed key and `login_method=legacy`. OAuth admission
uses `resolve_oauth_browser_subject` to check the login method, canonical key,
and active persisted user. Historical `app/app.py` handlers are not the
factory-owned contract. The separate `/api/challenge` flow creates a
`HODLXXI:login:<time>:<suffix>` message; it is not the LEGACY UUID flow and is not
silently accepted by this method. LNURL and Nostr login are also distinct.

The existing factory LEGACY handler checks session equality and a 600-second
age but does not implement the immutable proposal record or global consumption
required below. Its session challenge must not be reused as a device grant.

## Canonical bytes and method separation

Both repositories independently implement the same key-sorted, compact ASCII
JSON envelope, limited to 16,384 bytes, with exactly these members:

```text
content: exact existing canonical authorization/adoption semantic JSON STRING
context: the closed method-specific object below, or null
domain: HODLXXI_SOCIAL_MESSAGING_DEVICE_AUTHORIZATION_METHOD_V1
method: nostr_event_v1 | legacy_challenge_v1 | qr_desktop_v1
schema: hodlxxi.social_messaging_device_authorization_method.v1
version: integer 1
```

`authorizationDigest = SHA256(ASCII(envelope))`. For QR this is also the
`transcriptDigest`; there is no separately serialized human transcript. The
embedded content is validated through the existing device claim canonicalizers.
Its semantic digest and canonical binding-record ID retain their existing,
different meanings. All existing register/rotate/revoke/adopt fields, algorithms,
binding versions, predecessors, subjects, keys, request IDs, and intervals remain
committed byte-for-byte. Adopting authorizes the selected complete record; it
does not create a fourth binding operation or replace its key.

Parsers require the expected method out of band. Unknown/missing/duplicate
members, alternate encodings, fractional timestamps, booleans as versions,
noncanonical JSON, invalid X25519 keys, and method substitution fail closed.
Public failures contain no submitted values. Context timestamps are UTC-Z whole
seconds. `issuedAt <= now < expiresAt`; deadlines are exclusive, at most 300
seconds, and never exceed the applicable binding or pairing deadline.

`nostr_event_v1` has null context and retains the **unchanged** existing event
content, purpose, ordered tags, ID, and `nostr_event_id_bip340_v1` signature
format. Its method envelope is an inspection wrapper and does not replace the
existing wire payload, intent token, or evidence digest. NIP-07 and the existing
injectable one-shot NIP-46 adapter both supply this existing carrier. No claim
about the physical signer can be inferred from identical signature bytes.

## Independent phone login and device authorization

The phone generates a dedicated X25519 pair with
`generateKey({name: "X25519"}, false, ["deriveBits"])`. It stores the private
CryptoKey using IndexedDB structured clone and strict transaction completion,
then reads it back before requesting a bound login challenge. Only the public
key is exported. The dormant Social preparation seam reuses the existing local
device store and atomic add; it refuses replacement of an occupied slot. The
claimed public subject is initially only a local hint. Authentication must later
prove that same subject. No CryptoKey is used to authenticate or sign.

LEGACY context contains exactly `challenge` (canonical UUID-v4) and `loginContext`
(lowercase hex64 commitment to the original one-shot browser login transaction).
The existing semantic content supplies subject, deviceId, publicKey, requestId,
operation, binding version, predecessor, and expiry. Before the UUID is exposed
for signing, UBID must reserve the exact canonical envelope under the global
challenge and request identities. The record is immutable. Issuing a second
proposal for that UUID, even with another request ID, must fail. The injected
`issue_legacy_challenge` seam enforces reserve-before-release ordering.

The closed submission contains `method=legacy_challenge_v1`, `challenge`,
`loginContext`, `authorizationDigest`, `compressedPublicKey`, and `signature`.
The verifier receives the original record from trusted storage and the original
browser transaction context separately. Never accept a caller-supplied record
or replace it with an OAuth claim. A changed proposal or record digest cannot
match this original record even though the wallet signs only the opaque UUID.
The exact Bitcoin signature is checked locally without RPC in the pure seam.

Final canonical acceptance must atomically recheck the issued record, consume
the challenge and global request ID, verify Current-Full and exact lifecycle
state, and retain method-specific public evidence. Only then may the existing
login/OAuth continuation produce the independently authenticated Social session.
Login, authorization, and the continuation must be bound to that original
browser transaction; generic OAuth possession cannot supply missing evidence.
A successful bound LEGACY login needs no second NIP-07 signature.

## Desktop-approved phone pairing

1. An authenticated desktop explicitly selects **Add phone**. Social creates a
   one-shot offer through an authenticated confidential UBID coordination port.
   `create_pairing_offer` specifies independent CSPRNG 32-byte pairing ID and
   secret, a maximum 300-second TTL, the authenticated subject, and a random
   desktop context and compare-and-swap revision. No signer is acquired.
2. The QR contains exactly `hodlxxi-social-pair:v1:<hex64 pairingId>:<hex64 secret>`.
   This is a protocol locator, not a live route. A future URL adapter must place
   it in a fragment and immediately scrub it. It contains no raw subject,
   authorized login grant, reusable OAuth bearer, participant private key,
   X25519 private key, or message key. Locator possession allows a proposal only.
3. The phone scans, commits its own non-extractable device key, and generates a
   separate random 32-byte one-time exchange verifier. That verifier is transient
   phone state, never the messaging key. It submits its exact proposal and
   pairing possession proof. The pairing locator may cross only a confidential,
   no-store POST body, never logs, telemetry, persistence, or query strings.
4. QR context contains exactly `createdAt`, `desktopContext`, `exchangeCommitment`,
   `expiresAt`, `pairingId`, and `secretCommitment`. The source of subject,
   desktop context, pairing identity, and interval is the original offer.
   The phone cannot replace them. The immutable transcript includes that context
   and the exact derived semantic claim. Its deadline cannot extend the offer.
5. The secret commitment is SHA256 of ASCII
   `HODLXXI_SOCIAL_PAIRING_SECRET_V1 || NUL || lowercase-secret-hex`.
   The exchange commitment uses
   `HODLXXI_SOCIAL_PHONE_EXCHANGE_V1 || NUL || lowercase-verifier-hex`.
   Possession proof is HMAC-SHA256 keyed by the raw 32-byte pairing secret over
   ASCII `HODLXXI_SOCIAL_PAIRING_POSSESSION_V1 || NUL || transcriptDigest`.
   Verifiers check both the secret commitment and the exact HMAC. The first
   pending transcript wins an atomic claim of the offer; replacement is rejected.
6. Both devices independently display the first 12 hex digits of the transcript
   digest, uppercase in three groups of four. This 48-bit comparison code is
   human verification, not a password or authorization proof. Desktop approval
   displays the exact phone deviceId, X25519 public key, action, version,
   predecessor, and deadline from that same transcript. No editable label is
   treated as a cryptographic device identity.
7. Only explicit **Approve phone**, after comparing codes, may claim the current
   desktop revision, acquire NIP-07, compare its key to the authenticated session
   subject, and call `signEvent` once. The Social seam rechecks subject, revision,
   pairing and transcript after asynchronous boundaries and before signing.
   Startup, reconciliation, Add phone, scanning and future polling have no signer
   access. The provider is not retained. Changed context or cancellation fails.
8. The private never-published kind-27236 event has `content=exact method envelope`,
   `created_at=semantic issuedAt`, `pubkey=subject`, and ordered tags:

   ```text
   [purpose, hodlxxi-social-messaging-device-qr-approval-v1]
   [semantic-digest, transcriptDigest]
   [request-id, requestId]
   [action, register|rotate|revoke|adopt]
   [pairing-id, pairingId]
   [transcript, transcriptDigest]
   ```

   Event ID is SHA256 of compact NIP-01 `[0,pubkey,created_at,27236,tags,content]`.
   The signature format stays `nostr_event_id_bip340_v1`. Both repositories
   reconstruct the event, verify its ID and BIP340 signature, and reject the
   ordinary NIP-07 carrier substituted for QR approval or vice versa.
9. Social persists only exact public event retry material before any future
   submission. Retry cannot acquire another signer. UBID independently verifies
   the original offer, pending transcript, comparison code, authenticated
   desktop context, signature, expiry, Current-Full, exact lifecycle state,
   revision, and all replay identities before canonical acceptance.
10. Only that acceptance of an active register, rotate or adopted binding permits
    one device-bound session exchange; revocation cannot authorize phone login. The phone
    presents its separate verifier; possession of the QR secret is insufficient.
    Consumption, the original accepted revision, and future session issuance
    must share one atomic owner. The new pure exchange seam returns a closed
    `hodlxxi.social_phone_session_exchange_identity.v1` object, not a bearer.
    Its exact fields and bytes are frozen in both repositories' fixed vectors.
    This metadata belongs to the confidential session issuer. A browser cannot
    present a copied identity object as login authority.
11. The phone receives its own opaque Social session and reconciles an
    authoritative binding snapshot against its retained deviceId, public key,
    binding ID and version before becoming ready. A missing, changed, revoked,
    expired or ambiguous snapshot cannot be replaced by the exchange response.

Stealing the QR can create a pending proposal or deny service by winning the
one-shot scan. It cannot sign desktop approval or silently change the comparison
code on the genuine phone. Cancellation, expiry, repeated scanning, replaced
revisions, accepted replay, and consumed exchange state must fail closed. The
tests use an exact synthetic atomic port; there is no in-memory production store.

## Replay, evidence, and runtime boundary

All methods use the existing global `request:<requestId>` namespace, plus
`authorization:<method-envelope-digest>`. LEGACY also consumes
`legacy-challenge:<UUID>`; QR also consumes `pairing:<pairingId>`. Reservation is
not acceptance. These names specify logical namespaces to map to the existing
transaction/replay machinery, not a new parallel live ledger.

Pure parsers return candidates. Method verifiers retain the exact public proof;
the acceptance seam cryptographically re-verifies it and requires a
transaction-bound Current-Full verifier plus an atomic acceptance port. Missing
ports and caller-shaped acceptances fail. The port must recheck authoritative
register/adopt/rotate/revoke eligibility and predecessor, immutable issuance or
pairing state, and replay identities inside the same transaction. The returned
acceptance must exactly match the candidate's subject, request, digest and
canonical binding ID. It cannot grant Full or operator status.

Existing NIP-07/NIP-46 accepted retries, including expired exact replay,
authoritative reconciliation, public internal-route denials, confidential client
authentication, key storage, and default-off behavior are unchanged. New mobile
commands reject expiry; a later durable adapter must recover an already-accepted
exact result from immutable evidence before considering a fresh command. It
must never extend expiry or resign automatically. These dormant seams do not
activate the existing routing verifier for mobile evidence and must not relabel
a Bitcoin signature as a BIP340 signature.

No participant secret, serialized X25519 secret, or K_message is accepted or
returned. The only private-key persistence exception is the existing dedicated
non-extractable messaging CryptoKey stored device-locally by structured clone.
The exchange verifier is unrelated, one-time authentication state; it never
uses that CryptoKey. No relay, NIP-46 transport, account, discovery, polling,
fallback, or wallet vendor API is defined here.

## Required later integration and verification

The next phase must implement durable immutable challenge reservations, atomic
mobile evidence/lifecycle acceptance, and the challenge-bound OAuth continuation
before claiming mobile onboarding works. QR needs the corresponding durable
offer/revision/consumption owner and session issuer, then explicit UI integration.
Existing routes remain unchanged until those boundaries are reviewed together.

The identical `tests/fixtures/social_mobile_device_authorization_v1.json` files
contain independently checked semantic, method, binding, event, Bitcoin-message,
comparison, HMAC, and exchange-identity vectors for all four operations. Tests
verify signatures with existing cryptographic implementations, not permissive
signature mocks. Transaction and browser seams use explicit offline doubles.
No Redis/PostgreSQL, wallet, OAuth service, relay, staging or production runtime
is contacted to verify this phase.
